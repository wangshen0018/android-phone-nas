## 0. 一句话

**把手机里堆积的照片视频搬进自有存储，在你还记得的时候把「这是什么事」一次钉死，十年后靠这句话把照片找回来。**

---

## 1. 定位：三个不做，一个必须

这个项目不是相册管理软件。分界画在「谁的痛」上：

| 商业相册 App 在解决 | 本项目在解决 |
|---|---|
| 新拍的照片怎么看好、怎么修、怎么发 | 旧照片放哪、堆成山、忘了为什么拍 |
| 容量来自厂商云，超出就收费 | 容量来自你插的卡、闲置的硬盘 |
| 按时间流 + 人脸自动分组 | 按「事件」人工判定后固化 |
| 核心动作：浏览、编辑、分享 | 核心动作：批量搬入 → 判定归属 → 归档留痕 → 按事取用 |
| 数据在平台账号里 | 数据在本地普通目录里，账本可读可迁 |

**三个不做**

1. 不做人脸识别与 AI 自动分类。人脸回答「这是谁」，回答不了「为什么拍」；识别错了修误判比重标更累。
2. 不做在线修图、不做信息流。这是仓库，不是社交场。
3. 不做自动删除手机原片。收取永远是「复制 + 回执」，删不删由人决定。丢过一次照片的软件，没人敢再用第二次。

**一个必须**

每个事件必须留**一句人写的话**。这是整套系统唯一无法自动化的环节，也是全部价值所在。

## 2. 竞品调研结论（2026-11）

| 软件 | 强项 | 为什么不能直接用 |
|---|---|---|
| **Immich** | 功能最全：手机后台自动备份、人脸、CLIP 语义搜索、多用户、共享相册、去重 | 官方 6GB 内存起、推荐 8GB+4核，必须 PostgreSQL+Redis+ML 三容器。社区移植到安卓（`immich-native-android`）需 proot Debian + 重编译 sharp/onnx/insightface，作者自述「环境极度敏感、部署极其复杂」，还要 Shizuku 关 Phantom Process Killer。**最关键：它把文件重排进自己的 upload 目录，按上传日期+内部 ID 命名，磁盘上打开看不出是什么**，与「长期冷存、脱机可读」直接冲突 |
| **PhotoPrism** | 索引现有目录而不移动文件，元数据最专，2–3GB 可跑，稳定 | 手机端只有 PWA，无后台自动上传；分类靠 AI 标签；没有「存入批次」概念；没有判定流程 |
| **Photoview** | 目录即相册，自带密码分享链接，ARM 可跑，最轻 | 只负责把文件夹渲染成相册。事件要自己先建好文件夹，无聚类、无待判区、无回执，等于没把归类做成流程 |
| **PhotoStructure** | 最接近事件思想：when/where/what 分面浏览、自动分堆、去重强、文件留在原处、元数据随文件走、JSONL 同步报告 | 闭源商业软件需付费；桌面/Docker 程序，**没有旧手机当服务器这条路**；堆由算法生成，不要求人下结论；无「存入时间 vs 拍摄时间」双视角 |
| **LibrePhotos** | 自动 events、人脸、相册 | events 是算法生成的，不能人工命名固化；Django+PostGIS+Redis+ML，不轻 |
| **PiGallery2** | 专为树莓派级低配设计 | 只有浏览，无归档流程 |
| **Lomorage** | 手机照片备份到自有电脑/树莓派，定位接近 | 只管备份与浏览，无事件分类 |
| **KPhotoAlbum** | 按人、地点、事件、类别人工标注检索，理念最接近 | 纯桌面软件，无手机服务端 |

**结论：三条同时要——人工判定事件 + 强制留用途 + 旧手机能一键跑 + 磁盘目录脱机可读，市面上没有。**

所有工具都在解决「怎么找到照片」，没有一个解决「记住为什么拍」。那块空白就是本项目的全部立身之本。

### 2.1 可以直接吸收的做法

| 来源 | 吸收什么 | 怎么用 |
|---|---|---|
| PhotoStructure | JSONL 追加式同步报告，一行一事件，状态由最后一行决定 | 账本 `ledger.jsonl` 已经是这个模型，保持追加不覆盖 |
| PhotoStructure | 分面浏览（when / where / what） | 事件内「按存入 / 按拍摄」双视角即最小分面 |
| Photoview | 目录即相册的索引方式 | 归档区目录结构直接就是相册，事件不额外定义数据表 |
| PhotoPrism | 不移动、不改名、sidecar 存元数据 | 归档只复制，事件说明写 sidecar，不动 EXIF |
| Immich | 「手机端是入口」的体验标准 | 但改用「插卡/局域网搬入」实现，不引入容器 |

## 3. 五条设计铁律

1. **文件优先，数据库可弃。** 归档区就是普通目录，事件以文件夹命名。删掉本系统全部代码，文件仍能被任何文件管理器读懂，也仍能被 PhotoPrism / Photoview 直接索引。
2. **只复制，不移动原件。** 从手机收取时源文件保持原样；归档在库内部搬移。
3. **写操作必须留痕。** 每一次收取、归档、改名、修正都追加一条 JSONL。出现「无存档回执」即是缺陷，不是正常状态。
4. **时间语义只有一个来源。** 拍摄时间读文件 mtime（`mv` 会保留）；存入时间只认账本。永远不靠目录 mtime，它会被批量操作抹平。
5. **低配优先。** 目标机是 3–4GB 内存、无 GPU 的旧安卓。任何需要常驻 JVM/Python/容器组件的方案直接否决。

## 4. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│ 接入层  手机 App（WebView + 内置服务）                     │
│         电脑浏览器 / 电视 / 家人手机（局域网 or 组网）       │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTP
┌───────────────────────────┴─────────────────────────────┐
│ 展示层  index.html    向导 · 入口 · 状态卡片               │
│         archive.html  存档：年 → 事件 → 双视角 → 大图/播放   │
│         judge.html    判定：待判队列 · 批量确认 · 已完成     │
│         stats/diag    统计与自检                          │
│         （5244 alist） 全盘文件浏览（现成组件，不重写）       │
└───────────────────────────┬─────────────────────────────┘
                            │ CGI（busybox httpd :8083）
┌───────────────────────────┴─────────────────────────────┐
│ 业务层  ingest   收取：adb / 局域网 → inbox，写回执         │
│         cluster  聚类：时间断点 + 来源前缀 → 候选事件        │
│         decide   判定：批量写 decisions.jsonl             │
│         archive  归档：搬进 archive/<YYYY-MM>/<事件>，写账本 │
│         index    索引：receipts ∪ ledger → 事件时间线        │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────┴─────────────────────────────┐
│ 服务层  busybox httpd :8083   静态页 + CGI，单线程           │
│         alist :5244           全盘文件浏览 / WebDAV 挂载     │
│         thumb 工厂            320px 统一缩略图（图片缩放/抽帧）│
│         daemon.sh             后台轮转：缩略图预热、GC、巡检   │
│         Tailscale             组网，外网访问                │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────┴─────────────────────────────┐
│ 存储层  inbox/       待判区（按拍摄日期分目录）              │
│         archive/     归档区，按 YYYY-MM/事件名 分目录        │
│         state/       账本、缩略图缓存、状态缓存              │
│         外置卡       可整体改挂到 SD 卡，路径只在一处配置      │
└─────────────────────────────────────────────────────────┘
```

数据只向上流动一次，展示层不参与任何判断：**所有「判断照片属于哪个事件」的逻辑只存在于业务层**，前端只负责显示与收集输入。这样换 UI、换 App 壳都不影响数据正确性。

## 5. 存储布局

当前实测布局（K40，magisk 环境）：

```
/data/media/0/nasbak/
├── inbox/                         待判区
│   └── 2026-05-12/                ← 按拍摄日期自动分桶
│       ├── IMG_20260512_101133.jpg
│       └── VID_20260512_101530.mp4
├── archive/                       归档区（对用户可见的正式库）
│   └── 2026-05/
│       └── 老宅翻修-屋面防水验收/   ← 事件 = 目录名
│           ├── IMG_20260512_101133.jpg
│           └── _event.json        sidecar：一句话说明、标签、判定人
├── state/                         机器状态（可删可重建，除账本外）
│   ├── ledger.jsonl               搬移账本（唯一搬移真相）
│   ├── receipts.jsonl             收取回执（唯一「存入」真相）
│   ├── decisions.jsonl            判定记录（可重放出事件目录）
│   ├── thumbs/                    320px 缩略图缓存
│   ├── media/                     片段缓存
│   └── status-cache.json          面板状态卡缓存
└── _dup_backup/                   重复文件隔离区
```

**可移植设计（待实现）**：根路径 `${NASBAK_ROOT}` 只在一处配置，改成 `/storage/XXXX-XXXX/nasbak` 即整体迁到 SD 卡。归档区与状态分开，便于「状态留在内置存储、归档放外置卡」。

**事件目录命名规则**

```
<YYYY-MM-DD> <事件名>
```

- 日期前缀取事件内最早拍摄时间，保证目录按时间自然排序，脱离本系统也能按时间浏览。
- 事件名允许中文、空格、`-`、`·`；禁止 `/ \ : * ? " < > |` 和换行（与 Windows 互拷安全）。
- 重名自动加 `(2)`、`(3)`，不覆盖。
- 示例：`2024-05-12 老宅翻修-屋面防水验收`。

## 6. 数据模型：三个 JSONL

全部追加写，永不改写历史行。状态由同一 key 的最后一行决定（PhotoStructure 同步报告模式）。

### 6.1 `receipts.jsonl` — 收取回执

```json
{"ts":1715480000,"t":"2026-05-12T10:11:33+0800","id":"a1b2c3d4e5f60718","name":"IMG_20260512_101133.jpg","size":3145728,"src":"/sdcard/DCIM/Camera","dst":"inbox/2026-05-12","act":"arc","batch":"20260512T1011-7f3a"}
```

| 字段 | 含义 |
|---|---|
| `ts` | 秒级时间戳。**这就是「存入时间」，唯一权威值** |
| `id` | 内容哈希前 16 位 hex，去重与缩略图主键 |
| `act` | `recv` 已收进待判区 / `arc` 已归档 / `dup` 判为重复 |
| `batch` | 一次收取的批次号，前端「按存入批次分组」直接用这个字段 |
| `src` | 源路径，用于反查「这批是从哪个目录搬来的」 |

### 6.2 `ledger.jsonl` — 搬移账本

```json
{"ts":1715480100,"t":"2026-05-12T10:15:00+0800","id":"a1b2c3d4e5f60718","name":"IMG_20260512_101133.jpg","size":3145728,"act":"arc-move","from":"inbox/2026-05-12","to":"archive/2026-05/老宅翻修-屋面防水验收"}
```

`act` 取值：`recv`（K80→K40）、`mvdate`（inbox→日期桶）、`arc-move`（归档搬移）、`arc-renamefile`（文件重命名）、`dup`（隔离重复）、`undo`（撤销）。

**为什么需要两份**：回执记「什么时候进来的」，账本记「东西被搬去哪了」。手工移动文件只会在账本里产生记录，回执不会变——所以「存档时间」必须两源合并、取最早的那条，否则手工整理过的文件会显示「无存档回执」。

### 6.3 `decisions.jsonl` — 判定记录

```json
{"ts":1715480200,"ids":["a1b2c3d4e5f60718","..."],"event":"老宅翻修-屋面防水验收","ym":"2026-05","note":"东屋漏水返修，第三遍防水","who":"owner","act":"assign"}
```

可完全重放：删掉 `archive/` 全部目录，按 `decisions.jsonl` 重跑归档即可恢复同样的库。这是「数据库可弃」的兜底。

### 6.4 sidecar `_event.json` — 事件元数据

写进事件目录，跟照片在一起：

```json
{"event":"老宅翻修-屋面防水验收","date":"2026-05-12","note":"东屋漏水返修，第三遍防水，验收时发现檐口还是渗","tags":["房屋","施工"],"count":96,"firstArc":1715480100}
```

sidecar 而非改 EXIF：不改原图字节，跨软件可读，PhotoPrism/Photoview 忽略它也不影响。

## 7. 事件模型

**一个事件 = 一段连续时间 + 一个用途标签 + 一句人话。**

系统不定义事件，只负责把「可能属于同一件事」的照片推到你面前，剩下由人决定。

| 概念 | 定义 | 谁产生 |
|---|---|---|
| 候选堆（cluster） | 拍摄时间间隔 < `GAP`（默认 90 分钟）且来源前缀相同的一组 | 算法 |
| 事件（event） | 一个命名的目录 + sidecar | 人判定 |
| 存入批次（batch） | 一次收取动作 | 系统 |
| 拍摄日（shotDay） | 文件 mtime 的日期 | 系统 |

三个时间轴必须区分清楚，混在一起就是所有照片软件「找不到东西」的根因：

- **拍摄时间**：那一刻按快门。读 mtime。
- **存入时间**：搬进库房那一刻。读账本/回执。
- **判定时间**：你给它命名那一刻。读 decisions。

约束（已踩过的坑，写进契约）：

- **busybox httpd 不认 CGI 的 `Status:` 头**，重定向一律改成直出 `Content-Type` + 正文。
- **POST 下取不到 `QUERY_STRING`**，参数只从 body 读。
- body 上限 32KB；单次判定建议 ≤40 条。
- `Range` 请求返回 206 时 `Content-Type` 会被改成 `text/html`，视频仍可播，不要据此判错。

## 9. 关键流程

### 9.1 收取

```
手机相册 ──(adb pull / 局域网 SMB / 插卡直读)──> inbox/<拍摄日>/
                                              │
                                    每文件一条 receipts{act:recv,batch}
```

- 只读源、只写目标，源不动。
- 同名同 size 且哈希相同 → `act:dup`，进 `_dup_backup`，不重复占空间。
- 一次收取生成一个 `batch`，前端据此展示「2026-05-12 10:11 搬入 312 个」。

### 9.2 聚类候选

```
inbox 全量 → 按 mtime 升序 → 相邻间隔 > GAP 或来源前缀不同则断堆
           → 每堆带：张数、起止时间、总大小、代表缩略图
```

聚类只用于**排序和呈现**，不落库。判定结果才是数据。

### 9.3 判定

```
judge.html 拉待判 → 人勾选 + 填事件名 + 填一句话
  → 每 20 条一批 POST decide.cgi（带 cats）
  → 整批失败自动回退逐条，定位问题文件
  → decisions.jsonl 追加 → daemon 拾取 → archive 搬移 + 写账本
```

已踩过的坑：`renderTiles()` 提前 return 会导致「确认归档」永久 disabled——状态刷新必须无条件执行。

### 9.4 归档

```
以 decisions 最新一行 → 目标目录 archive/<ym>/<event>/
  mkdir -p → mv 逐文件 → ledger{act:arc-move} → 写 _event.json
  → 更新 receipts 的 act 为 arc
```

`mv` 在同一文件系统内是改名，保留 mtime，因此拍摄时间不会丢。跨文件系统（内置→SD 卡）才需要 `cp -p` + 校验 + 删源，此时必须校验 md5。

### 9.5 浏览与索引

```
archive.cgi 组装：
  文件树（archive/ 目录扫描）
  ∪ 回执时间（receipts act=arc）
  ∪ 账本时间（ledger act=arc-move / arc-renamefile）
  → 每文件得到 shot（拍摄）、arcTs（存入）、batch（批次）
  → 前端按 mode 分组
```

## 10. 双视角分组算法

同一事件内，`#batchBtn` 切换两种分组，服务两种回忆方式：

| 模式 | 分组键 | 回答的问题 | 默认 |
|---|---|---|---|
| 按存入 | `batch`（一次搬入） | 「我上次一口气整理的那批在哪」 | ✅ |
| 按拍摄 | `shotDay` + 上下午 | 「那天上午和下午分别拍了什么」 | — |

规则：

- 存入模式：`batch` 缺失（老数据或手工移动）时归入「更早存入」，**不显示「无记录」**，避免出现看起来像故障的空白。
- 拍摄模式：连续两天内的照片若属同一事件，合并为一组并标注「跨 2 天」。
- 两种模式下文件顺序都按拍摄时间升序，缩略图延迟加载，先铺 320px 占位再换原图。

## 12. 首次使用向导

目标：亲戚朋友拿到旧手机，只做两件事——插卡、连 WiFi。其余全部由页面引导。

| 步骤 | 页面做什么 | 用户做什么 |
|---|---|---|
| ① 选库房 | 列出所有可写卷（内置 / SD / U 盘），显示剩余容量与建议 | 点一下选择 |
| ② 连起来 | 检测组网软件是否已装；未装则给下载入口与图文引导（Tailscale 类），装完点「已安装」自动读取本机 IP 并配对 | 装一个 App，扫码/登录 |
| ③ 定管理员 | 设置「存档管理员」密码，区分三种角色 | 设一次密码 |

角色模型（两元，无分享、无访客）：

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **管理员**（owner） | 收取、判定、归档、改事件名、删除、改设置 | — |
| **浏览**（viewer） | 看存档、看大图、播视频、上传 | 判定、归档、删除、改名、进设置 |

设计取舍：

- **不做账号体系，不做登录页。** 一台设备就是一个家，两个角色用「模式」表达，不用用户名密码。切换靠管理员 PIN，PIN 存在 `config.json` 里。
- **浏览模式可以免 PIN。** 默认进入就是浏览模式；要从浏览切回管理员，弹一次 PIN 输入。
- **不生成任何对外链接。** 想看照片必须连到这台设备（局域网或组网），没有"发个链接给亲戚"这条路。少一个功能，少一整类安全风险。

配置落在 `state/config.json`，删掉即回到向导。

## 13. 交付形态

同一套 `www/` + `bin/`，三种外壳：

| 形态 | 适合 | 服务怎么跑 | 成本 |
|---|---|---|---|
| **A. 安卓 App（APK）** | 旧手机，最推荐 | App 内起本地 HTTP 服务，WebView 打开 `127.0.0.1:8083` | 免费、免开发者账号，GitHub Actions 出包 |
| **B. 电脑包** | 闲置笔记本/台式/小主机 | 解压即用，双击启动脚本，浏览器打开 | 最低门槛，可挂大容量硬盘 |
| **C. 纯浏览器（PWA）** | 已有 NAS 或服务器 | 放到任意静态服务 + CGI 环境 | 只当界面，不解决存储 |

统一约束：**首页地址必须是 `127.0.0.1`**。安卓上访问本机 Tailscale IP（100.64.x.x）不会回环，会白屏——这个坑已经踩过。

## 14. 安全边界

| 项 | 做法 |
|---|---|
| 网络暴露 | 只监听局域网；外网一律走组网虚拟 IP，不做端口映射与 DDNS |
| 对外链接 | **不提供**。系统不生成分享 URL、不生成 token，外网不可达除了组网成员 |
| 角色 | 浏览模式隐藏判定与删除入口；切回管理员需 PIN |
| 删除 | 默认移入回收区，定期 GC；永久删除需二次确认 |
| 上传 | 拦截可执行扩展名；原文件名只作显示，落盘用哈希前缀 |
| 凭据 | 不入仓库；`deploy/scrub-rules.ps1` 在公开仓库推送前剔除密钥与内部路径 |

## 16. 待定问题

1. **外置卡根路径迁移**：`inbox` 与 `archive` 迁到 SD 卡、`state` 留内置，还是全迁？影响 `mv` 是否跨文件系统（跨则必须 `cp -p` + md5 校验）。
2. **手工移动文件的回执补齐**：是继续靠「两源取最早」自动兼容，还是在文件管理器移动后由守护进程扫描补账？后者更准但需要额外遍历。
3. **事件名的可读性 vs 唯一性**：允许同名事件（不同月份）还是强制全局唯一？当前按月目录，天然可重名。
4. **PIN 校验的接口层落地**：当前 P3 只在界面层遮蔽危险入口（浏览模式隐藏判定与删除），CGI 侧尚未校验 PIN。下一步在 `decide.cgi` / `apply.cgi` 增加校验，规则为「config 里 PIN 为空则不校验」（保证老设备升级无感）。
5. **旧电脑包的技术选型**：Windows 上跑 CGI 需要额外运行时，是否改用一个小型静态服务 + 本地脚本，代价是维护两套服务层。
6. **8083 曾自行停止**，原因未查明；P3 需要在 App 壳内做进程守护与看门狗。
